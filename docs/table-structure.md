# Table Structure — Hospital OPD Appointment Booking Platform

**Schema / workspace:** `NOV_2026_BATCH` (Oracle 23ai, APEX 26.1, Mumbai region)
**Source of truth:** `database/01_create_tables.sql` — this page is the readable summary for the report.

## Standards applied to all 10 tables

| Rule | Implementation |
|---|---|
| Naming | `GIRISH_` prefix on tables, sequences, indexes, triggers; ≤ 30 characters |
| Surrogate key | `NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY`, named `PK_…` |
| Business key | `UNIQUE` constraint where the real world demands it (email, phone, UHID, booking reference) |
| WHO audit | `CREATED_BY`, `CREATED_DATE`, `LAST_UPDATED_BY`, `LAST_UPDATED_DATE` with DEFAULTs + `BEFORE UPDATE` trigger |
| Soft delete | `IS_ACTIVE CHAR(1) DEFAULT 'Y'` — master rows are deactivated, never deleted |
| Normal form | 3NF — `APPOINTMENTS` holds `SLOT_ID` + `PATIENT_ID` only; the doctor is reached via `SLOTS.DOCTOR_ID` |
| Business rules | stored as rows (`GIRISH_CANCELLATION_RULES`), not hard-coded |
| Constraints | named `PK_ / UK_ / CK_ / FK_` so error messages and the API error map stay readable |

*The four audit columns are present in every table below and are not repeated in each column list.*

## 1. GIRISH_DEPARTMENTS — hospital specialties

| Column | Type | Constraint |
|---|---|---|
| `DEPT_ID` | NUMBER | PK, identity |
| `DEPT_CODE` | VARCHAR2(10) | NOT NULL, UNIQUE |
| `DEPT_NAME` | VARCHAR2(100) | NOT NULL, UNIQUE |
| `FLOOR_NO` | NUMBER(3) | — |
| `IS_ACTIVE` | CHAR(1) | DEFAULT 'Y', CHECK (Y/N) |

Used by: doctor directory search, department filter, no-show-by-department report.

## 2. GIRISH_DOCTORS — doctor master profile

| Column | Type | Constraint |
|---|---|---|
| `DOCTOR_ID` | NUMBER | PK, identity |
| `DEPT_ID` | NUMBER | NOT NULL, FK → DEPARTMENTS (delete restricted) |
| `EMP_CODE` | VARCHAR2(20) | NOT NULL, UNIQUE |
| `FULL_NAME` | VARCHAR2(120) | NOT NULL |
| `QUALIFICATION` | VARCHAR2(120) | — |
| `EMAIL` | VARCHAR2(150) | NOT NULL, UNIQUE |

| `ROOM_NO` | VARCHAR2(15) | — (printed on the booking slip) |
| `CONSULT_FEE` | NUMBER(8,2) | NOT NULL, CHECK ≥ 0 |
| `LANGUAGES` | VARCHAR2(120) | — (search filter) |
| `IS_ACTIVE` | CHAR(1) | DEFAULT 'Y', CHECK (Y/N) |

## 3. GIRISH_SLOT_TEMPLATES — the weekly plan that drives slot generation

| Column | Type | Constraint |
|---|---|---|
| `TEMPLATE_ID` | NUMBER | PK, identity |
| `DOCTOR_ID` | NUMBER | NOT NULL, FK → DOCTORS ON DELETE CASCADE |
| `DAY_OF_WEEK` | NUMBER(1) | NOT NULL, CHECK 1–7 (1 = Monday) |
| `START_TIME` | VARCHAR2(5) | NOT NULL, 'HH24:MI' |
| `END_TIME` | VARCHAR2(5) | NOT NULL, CHECK end > start |
| `SLOT_MINUTES` | NUMBER(3) | DEFAULT 15, CHECK 5–120 |
| `MAX_PATIENTS` | NUMBER(3) | DEFAULT 1, CHECK 1–50 (seats per slot) |
| `EFFECTIVE_FROM` | DATE | DEFAULT TRUNC(SYSDATE) |
| `EFFECTIVE_TO` | DATE | nullable = open ended |
| `IS_ACTIVE` | CHAR(1) | DEFAULT 'Y' |

`UNIQUE (DOCTOR_ID, DAY_OF_WEEK, START_TIME)` — no duplicated template row, so generation is repeatable.
Example row: Dr. Sharma, day 1, 09:00–13:00, 15 min, 2 patients per slot.

## 4. GIRISH_SLOTS — concrete dated slots (what patients actually book)

| Column | Type | Constraint |
|---|---|---|
| `SLOT_ID` | NUMBER | PK, identity |
| `DOCTOR_ID` | NUMBER | NOT NULL, FK → DOCTORS ON DELETE CASCADE |
| `TEMPLATE_ID` | NUMBER | FK → SLOT_TEMPLATES ON DELETE SET NULL (provenance only) |
| `SLOT_DATE` | DATE | NOT NULL |
| `START_TIME` | VARCHAR2(5) | NOT NULL |
| `END_TIME` | VARCHAR2(5) | NOT NULL, CHECK end > start |
| `MAX_CAPACITY` | NUMBER(3) | DEFAULT 1, CHECK 1–50 |
| `CURRENT_BOOKINGS` | NUMBER(3) | DEFAULT 0, **CHECK BETWEEN 0 AND MAX_CAPACITY** |
| `STATUS` | VARCHAR2(10) | DEFAULT 'AVAILABLE', CHECK (AVAILABLE/BOOKED/BLOCKED) |

`UNIQUE (DOCTOR_ID, SLOT_DATE, START_TIME)` — one physical slot per doctor per time; makes
`GENERATE_SLOTS` safe to re-run.
`CK_GIRISH_SLOT_CAPACITY` is the database-level guarantee against overbooking, independent of the
PL/SQL row lock.

## 6. GIRISH_APPOINTMENTS — the core transaction

| Column | Type | Constraint |
|---|---|---|
| `APPOINTMENT_ID` | NUMBER | PK, identity |
| `BOOKING_REF` | VARCHAR2(20) | NOT NULL, UNIQUE (e.g. `OPD-202611-00042`) |
| `SLOT_ID` | NUMBER | NOT NULL, FK → SLOTS |
| `PATIENT_ID` | NUMBER | NOT NULL, FK → PATIENTS |
| `STATUS` | VARCHAR2(12) | DEFAULT 'HELD', CHECK (HELD/CONFIRMED/CHECKED_IN/COMPLETED/CANCELLED/NO_SHOW/EXPIRED) |
| `CONSULT_FEE` | NUMBER(8,2) | price snapshot, CHECK ≥ 0 |
| `BOOKED_AT` | TIMESTAMP(6) | DEFAULT SYSTIMESTAMP |
| `HOLD_EXPIRES_AT` | TIMESTAMP(6) | **CHECK: required while STATUS = 'HELD'** (5-minute TTL) |
| `CONFIRMED_AT` / `CHECKED_IN_AT` / `COMPLETED_AT` / `CANCELLED_AT` | TIMESTAMP(6) | audit of each transition |
| `CANCEL_REASON` | VARCHAR2(400) | — |

Deliberately **no** `DOCTOR_ID`: it is reachable via `SLOT_ID → SLOTS.DOCTOR_ID`. Storing it again
would be a transitive dependency (3NF violation) and could contradict the slot's doctor.

## 7. GIRISH_TOKEN_QUEUE — daily physical queue

| Column | Type | Constraint |
|---|---|---|
| `TOKEN_ID` | NUMBER | PK, identity |
| `APPOINTMENT_ID` | NUMBER | NOT NULL, **UNIQUE**, FK → APPOINTMENTS ON DELETE CASCADE |
| `DOCTOR_ID` | NUMBER | NOT NULL, FK → DOCTORS ON DELETE CASCADE |
| `TOKEN_DATE` | DATE | DEFAULT TRUNC(SYSDATE) |
| `TOKEN_NO` | VARCHAR2(12) | NOT NULL, e.g. `CARD-04` |
| `QUEUE_STATUS` | VARCHAR2(10) | DEFAULT 'WAITING', CHECK (WAITING/CALLED/DONE/SKIPPED) |
| `CALLED_AT` | TIMESTAMP(6) | — |

`UNIQUE (APPOINTMENT_ID)` makes check-in idempotent (double-clicking cannot mint two tokens).
`UNIQUE (DOCTOR_ID, TOKEN_DATE, TOKEN_NO)` keeps each doctor's daily token series clean.

## 8. GIRISH_PAYMENTS — append-only money ledger

| Column | Type | Constraint |
|---|---|---|
| `PAYMENT_ID` | NUMBER | PK, identity |
| `APPOINTMENT_ID` | NUMBER | NOT NULL, FK → APPOINTMENTS ON DELETE CASCADE |
| `ENTRY_TYPE` | VARCHAR2(10) | DEFAULT 'CHARGE', CHECK (CHARGE/REFUND) |
| `PAYMENT_MODE` | VARCHAR2(10) | NOT NULL, CHECK (UPI/CARD/CASH/NETBANKING/WALLET) |
| `TXN_REF` | VARCHAR2(40) | UNIQUE (nullable) — simulated gateway reference |
| `AMOUNT` | NUMBER(8,2) | NOT NULL, CHECK > 0 |
| `STATUS` | VARCHAR2(10) | DEFAULT 'SUCCESS', CHECK (SUCCESS/REFUNDED/FAILED/PENDING) |
| `PAID_AT` | TIMESTAMP(6) | DEFAULT SYSTIMESTAMP |

One `CHARGE` row on confirm; a `REFUND` row is appended on cancellation, so the refund history is
never overwritten.

## 9. GIRISH_CANCELLATION_RULES — refund policy as data

| Column | Type | Constraint |
|---|---|---|
| `RULE_ID` | NUMBER | PK, identity |
| `RULE_NAME` | VARCHAR2(100) | NOT NULL, UNIQUE |
| `MIN_HOURS_BEFORE` | NUMBER(6,2) | NOT NULL, CHECK ≥ 0 |
| `MAX_HOURS_BEFORE` | NUMBER(6,2) | nullable = open-ended top band, CHECK > MIN |
| `REFUND_PERCENT` | NUMBER(5,2) | NOT NULL, CHECK 0–100 |
| `PENALTY_AMOUNT` | NUMBER(8,2) | DEFAULT 0, CHECK ≥ 0 |
| `IS_ACTIVE` | CHAR(1) | DEFAULT 'Y' |

Matched with `MIN_HOURS_BEFORE <= hours_before < MAX_HOURS_BEFORE`. Typical rows:
> 4 h → 100 % refund · 2–4 h → 50 % · < 2 h → 0 % + flat fee.

## 10. GIRISH_ERROR_LOG — diagnostic audit

| Column | Type | Constraint |
|---|---|---|
| `ERROR_ID` | NUMBER | PK, identity |
| `MODULE_NAME` | VARCHAR2(100) | NOT NULL |
| `ERROR_CODE` | VARCHAR2(20) | — |
| `ERROR_MESSAGE` | VARCHAR2(4000) | — |
| `BACKTRACE` | CLOB | `DBMS_UTILITY.FORMAT_ERROR_BACKTRACE` |
| `LOGGED_BY` | VARCHAR2(100) | DEFAULT APEX user / DB user |
| `LOGGED_AT` | TIMESTAMP(6) | DEFAULT SYSTIMESTAMP |

No `IS_ACTIVE` and no audit columns: rows are immutable diagnostics, and `LOGGED_BY` + `LOGGED_AT`
already are the WHO columns.

## Relationships at a glance

```
DEPARTMENTS 1 ─── N DOCTORS
DOCTORS     1 ─── N SLOT_TEMPLATES      (template → generated slots)
DOCTORS     1 ─── N SLOTS
SLOT_TEMPLATES 1 ── N SLOTS             (nullable, ON DELETE SET NULL)
PATIENTS    1 ─── N APPOINTMENTS
SLOTS       1 ─── N APPOINTMENTS        (N = MAX_CAPACITY)
APPOINTMENTS 1 ── 0..1 TOKEN_QUEUE      (UNIQUE appointment_id)
APPOINTMENTS 1 ── N PAYMENTS            (CHARGE + optional REFUND)
CANCELLATION_RULES ─ ─ ─ APPOINTMENTS   (logical: matched by hours-before on cancel)
```

## Indexes (11) — chosen for the app's actual query paths

| Index | Columns | Serves |
|---|---|---|
| `IX_GIRISH_SLOT_DOC_DATE` | DOCTOR_ID, SLOT_DATE, STATUS | availability lookup (hottest query) |
| `IX_GIRISH_SLOT_DATE_ST` | SLOT_DATE, STATUS | daily sweeps |
| `IX_GIRISH_APPT_PATIENT` | PATIENT_ID, BOOKED_AT DESC | My Bookings |
| `IX_GIRISH_APPT_STATUS` | STATUS, BOOKED_AT | status transitions, admin filters |
| `IX_GIRISH_APPT_HOLD` | STATUS, HOLD_EXPIRES_AT | expired-hold sweep |
| `IX_GIRISH_APPT_SLOT` | SLOT_ID | FK index (Oracle does not add one) + locking |
| `IX_GIRISH_TOKEN_DOC_DT` | DOCTOR_ID, TOKEN_DATE, QUEUE_STATUS | doctor's live queue |
| `IX_GIRISH_PAY_APPT` | APPOINTMENT_ID, ENTRY_TYPE | slip / receipt |
| `IX_GIRISH_DOC_DEPT` | DEPT_ID, IS_ACTIVE | doctor-by-department |
| `IX_GIRISH_DOC_NAME` | UPPER(FULL_NAME) | case-insensitive name search |

Plus sequence `SEQ_GIRISH_BOOKING_REF` for reference numbers (never `MAX()+1`).

## How to create these tables (order matters)

1. `database/00_drop_all.sql` — only when rebuilding an existing schema.
2. `database/01_create_tables.sql` — tables → indexes → sequence.
3. `database/02_audit_triggers.sql` — 9 `BEFORE UPDATE` triggers.
4. `database/99_verify_schema.sql` — expect 10 rows `CREATED`, FK/constraint/index inventories,
   and row counts of 0.

Run in **SQL Workshop → SQL Scripts** (paste → Run in Background) or paste block by block in
**SQL Commands**. All three files are re-runnable objects except the DDL, which is create-once by design.
